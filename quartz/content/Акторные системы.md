# 1	Теория акторов

The Actor Model was conceived in MIT's Artificial Intelligence labs back in the mid 1970's

**Акторы** - математическая модель [параллельных вычислений](https://ru.wikipedia.org/wiki/%D0%9F%D0%B0%D1%80%D0%B0%D0%BB%D0%BB%D0%B5%D0%BB%D1%8C%D0%BD%D1%8B%D0%B5_%D0%B2%D1%8B%D1%87%D0%B8%D1%81%D0%BB%D0%B5%D0%BD%D0%B8%D1%8F "Параллельные вычисления"), строящаяся вокруг понятия _актора_ ([англ.](https://ru.wikipedia.org/wiki/%D0%90%D0%BD%D0%B3%D0%BB%D0%B8%D0%B9%D1%81%D0%BA%D0%B8%D0%B9_%D1%8F%D0%B7%D1%8B%D0%BA "Английский язык") actor «актёр; действующий субъект»), считающегося универсальным примитивом параллельного исполнения. Тема граничит с распределенными вычислениями.


>Для реализации акторной системы я буду использовать: Python(фреймворк Thespian).

Актор в данной модели взаимодействует путём обмена сообщениями с другими акторами, и каждый в ответ на получаемые сообщения может принимать локальные решения, создавать новые акторы, посылать свои сообщения, устанавливать, как следует реагировать на последующие сообщения.

## 1.1	Фундаментальные концепции[^1]
Актор является вычислительной сущностью, которая в ответ на полученное сообщение может одновременно:
- отправить конечное число сообщений другим акторам;
- создать конечное число новых акторов;
- выбрать поведение, которое будет использоваться при обработке следующего полученного сообщения.

Отделение отправителя от посланных сообщений стало фундаментальным достижением модели акторов: тем самым обеспечивается асинхронная связь и управление структурами в виде формы передачи сообщений.

Получатели сообщений идентифицируются по адресу, который иногда называют «почтовым адресом». Таким образом, актор может взаимодействовать только с теми акторами, адреса которых он имеет, может извлечь адреса из полученных сообщений или знать их заранее, если актор создал их сам.

Дополнение:
- язык программирования [SmallTalk](https://ru.wikipedia.org/wiki/Smalltalk "Smalltalk")[[12]](https://ru.wikipedia.org/wiki/%D0%9C%D0%BE%D0%B4%D0%B5%D0%BB%D1%8C_%D0%B0%D0%BA%D1%82%D0%BE%D1%80%D0%BE%D0%B2#cite_note-12) построен исключительно на взаимодействии объектов посредством сообщений друг другу. Код каждого объекта при этом исполняется изолированно от соседей в параллельной среде.

После создания актора мы не можем вызывать его методы, дальнейшее  взаимодействие реализуется с помощью главного класса -  `ActorSystem`.
При создании своего класса актора мы наследуемся от базового класса `Actor`, как я понял для того, чтобы `ActorSystem` могла с ним работать.

Для отправки сообщения вызываем `tell`.
`Актор с адресом ActorAddr-/A~a получил Первое сообщение от  ActorAddr-System:ExternalRequester`, где ExternalRequester это ввод с консоли ввода.

**Асинхронные запросы**:  
Используйте `ask()` вместо `tell()`, чтобы получить результат операции сразу:
```python
future = actorSystem.ask(calculator_address, {"op": "add", "a": 2, "b": 3})
result = actorSystem.listen(future)  # result = 5
```

В используемом в примерах  фреймворке ограничения на сообщения появляются при функционировании  акторов в распределенной системе: они должны быть сериализуемы в **формат  pickle** [https://docs.python.org/3/library/pickle.html].
### 2.1.1	 **Формат адресов в Thespian**
- Thespian использует внутренний формат для представления адресов, который не всегда удобочитаем. Например, строки вроде `//A~a` или `//B~7` — это стандартный формат адресов, и они означают разные уникальные актора в системе.
- Если вы видите такие адреса, это нормально и свидетельствует о том, что система работает корректно.

### 2.1.2	**Принципы чистой архитектуры в контексте акторной модели**

1. **Разделение ответственности (Single Responsibility)**:
    - **Раньше**:
        - `PairNumbersAgent` отвечал за хранение двух чисел и их отправку, дублируя логику `NumberActor`.
        - Калькулятор смешивал вычисления с управлением данными.
    - **Сейчас**:
        - **`NumberActor`** — только хранит значение и отвечает на запросы.
        - **`CalculatorActor`** — управляет операциями: запрашивает данные, выполняет вычисления, возвращает результат.
        - **Нет дублирования**: Все операции с числами (хоть с одним, хоть с двумя) обрабатываются через единый механизм запросов.
2. **Инкапсуляция**:
    - **Акторы-числа** не знают, как и где используются их значения. Они предоставляют данные только по запросу.
    - **Калькулятор** не имеет прямого доступа к состоянию других акторов. Он запрашивает данные через сообщения, соблюдая границы.
3. **Зависимости направлены к ядру**:
    - **Бизнес-логика** (вычисления) находится в `CalculatorActor` — это «ядро» системы.
    - **Акторы-числа** и инфраструктура (система акторов) — это «внешние слои», которые можно менять без изменения логики операций.
4. **Тестируемость**:
    - **`NumberActor`** можно тестировать изолированно, проверяя, что он корректно отвечает на запросы.
    - **`CalculatorActor`** тестируется с мок-акторами, имитирующими ответы с числами.
    - Пример теста для сложения:
```python 
def test_add_operation():
    calculator = CalculatorActor()
	mock_number1 = MockActor(response={"value": 5})
    mock_number2 = MockActor(response={"value": 3})

    calculator.send("perform_add",number1=mock_number1, number2=mock_number2)
     assert calculator.get_result() == 8
```

        
5. **Гибкость и расширяемость**:
    - Чтобы добавить **новую операцию** (например, умножение), нужно изменить только `CalculatorActor`, не трогая акторы-числа.
    - Чтобы добавить **поддержку трех чисел**, модифицируем логику ожидания результатов в калькуляторе:
 ```python
        # В CalculatorActo
        if len(operation["values"]) == 3:
            result = operation["values"][0] * operation["values"][1] * operation["values"][2]
```
#### **Пример: Как соблюдается чистая архитектура*
##### Сценарий: Вычисление суммы трех чисе
1. **Инициируем операцию**:
```python
    actorSystem.tell(calculator, {
        "perform_sum": True,
        "numbers": [number1, number2, number3]
    })
    ```
2. **Калькулятор** рассылает запросы всем трем акторам-числам.
3. **Каждый NumberActor** возвращает своё значение.
4. **Калькулятор** вычисляет сумму и возвращает результат
**Что изменилось**
- Ни `NumberActor`, ни система сообщений не потребовали изменений.
- Вся логика добавления операции с тремя числами инкапсулирована в `CalculatorActor`.
### 2.1.3	**Ключевые улучшения**

|Аспект|Было|Стало|
|---|---|---|
|**Дублирование кода**|`PairNumbersAgent` дублировал `NumberActor`|Единый `NumberActor` для любых операций|
|**Связность**|Калькулятор зависел от формата данных (списки vs числа)|Калькулятор работает через универсальные запросы|
|**Масштабируемость**|Для N чисел нужен новый актор|Поддержка N чисел «из коробки»|

### 2.1.4	**Как развивать систему дальше, соблюдая чистую архитектуру**

1. **Добавьте интерфейсы для сообщений**:  
    Определите классы-контракты для сообщений (например, `OperationRequest`, `ValueResponse`), чтобы форматы данных были явными.
    ``` python
    from dataclasses import dataclass
    
    @dataclass
    class OperationRequest:
        operation_id: str
        requester: ActorAddress
    
    @dataclass
    class ValueResponse:
        operation_id: str
        value: float
```
2. **Внедрите Dependency Injection**:  
    Передавайте зависимости (например, адрес калькулятора) через конструктор, а не через сообщения:
```python
    class NumberActor(Actor):
        def __init__(self, calculator_address: ActorAddress):
            super().__init__()
            self.calculator = calculator_address
```


3. **Логирование и мониторинг**:  
    Добавьте актор-логгер, который будет принимать события от всех компонентов. Это отделит инфраструктурный код от бизнес-логики.
4. **Обработка ошибок**:  
    Создайте типы сообщений для ошибок (например, `InvalidOperationError`), чтобы калькулятор мог их обрабатывать, не прерывая работу.
### 2.1.5	**Итог**
Предложенная архитектура:
- Соответствует принципам **чистой архитектуры** (разделение слоёв, инкапсуляция, тестируемость).
- **Устраняет дублирование** через универсальные акторы-числа.
- **Готова к масштабированию**: Добавление новых операций и типов данных не требует переписывания существующего кода.
Это делает систему гибкой, поддерживаемой и готовой к сложным сценариям (например, распределенные вычисления или конкурентные операции).
